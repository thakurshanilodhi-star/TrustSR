# Limitations

1. **Synthetic-only evidence:** fixtures, tests and notebook outputs validate code paths, not real-world recovery effectiveness.
2. **Trusted-key assumption:** Ed25519 verification is meaningful only when the public key is independently provisioned and trusted.
3. **Checkpoint cleanliness:** a valid signature cannot prove the checkpoint was uncontaminated when signed.
4. **Scope completeness:** matching IDs against a declared manifest checks internal consistency only; the manifest's content is an assumption about the real world.
5. **Audit storage:** the log is in-memory. A hash chain does not stop full rewriting without an out-of-band trusted head (`trusted_audit_head`) or remote append-only storage.
6. **Same-controller audit:** `recover_state` writes the events `verify_recovery` later checks. Both must run under a controller the attacker cannot rewrite; the log shows consistency, not the writer's honesty.
7. **Replay mark storage:** `HighWaterMark` is only as trustworthy as where it lives. Anyone who can rewrite the SQLite file can lower the mark. Unversioned checkpoints (`version=None`) offer no replay protection and are refused when a guard is used.
8. **Rollback:** `allow_rollback=True` is a deliberate operator override; it is logged but not authorised by anything in this package.
9. **Selective recovery:** with `keys=[...]` only those keys are verified; other keys are neither restored nor asserted clean.
10. **State comparison:** contamination detection is exact equality against the signed payload, not a causal or semantic detector.
11. **Graph policy:** `graph.py` only protects against missing edges that are *declared*. Undeclared missing edges and incomplete inventories are invisible (Lab 01.7).
12. **Canonical JSON:** deterministic (sorted keys, NaN/Infinity rejected) but not RFC 8785; avoid floats in signed payloads for cross-language use.
13. **External side effects:** restoring local state does not undo payments, messages, API calls, or other irreversible actions.
14. **Not implemented:** distributed agents, consensus, compromised keys, remote append-only storage, trusted timestamps, atomic audit-in-the-same-transaction as state (see Lab 02 FINAL caveat), and production integrations.
15. **Notebooks:** Labs 01-13 are self-contained and do not import the package; their saved outputs came from a plain-Python harness, not a Jupyter kernel.
16. **Report seal is in-process only:** `VerificationReport` is sealed with a per-process random HMAC key. It stops forged dicts, edited/copied/pickled reports and replayed reports, but not code running in the same interpreter that deliberately reaches into module internals. It is not valid across processes or restarts (a report cannot be stored and promoted later).
17. **`transition()` is a predicate:** it trusts the flags its caller passes. Use `TrustTracker`, which derives them from a sealed report, as the enforcement point.
18. **Anchor independence is a deployment property:** `HeadAnchor` (plain file) gives no protection against whoever controls the log's account. `SignedHeadAnchor` stops forging a head without the authority private key but not deletion/rollback to an older signed file (use `min_sequence`). `AnchorServer`/`RemoteHeadAnchor` is only independent if you run it under another OS account/host with its own key custody and TLS (`docs/anchor_deployment.md`). The unit tests run it on localhost in one account; no real second-host deployment was tested. The log itself is still in memory.
19. **Notebook reproducibility is partially evidenced:** `tools/run_notebooks.py` re-executes every notebook and compares the layout-insensitive token content of its text output with the saved output. This is a signal, not proof: random Ed25519 keys and timestamps are masked, bare integers up to three digits are ignored, and execution is a plain `exec()` harness, not a Jupyter kernel. Notebook runs have not been executed under Colab/Jupyter by this project.
20. **Initial trust state:** the tracker now refuses to initialize directly as `Trusted`; callers must use the verified promotion path. This is a code-level guard, not a protection against hostile code executing in the same Python process.
21. **No universal proof:** passing these tests is not a formal proof of correctness or security.
22. **Persistent-state commit is a reference implementation only:** `SqliteStateStore.commit_recovery` writes state + `recovery_id` + digest in one SQLite transaction, re-reads through a new connection and recomputes the digest; promotion is bound to a digest the caller re-reads right before promoting. It is not a production adapter for your agent's real store, and the store and the audit log remain two separate systems: a crash after the store commit but before the audit event leaves a `recovery_id` the log does not know, which fails verification (fail closed) and needs operator reconciliation. Whoever can rewrite the SQLite file can rewrite state, digest and `recovery_id` together.
23. **Promotion bindings are only as honest as their inputs:** `expected_checkpoint_sha256`, `expected_recovery_id` and `committed_state_sha256` are supplied by the calling code. The tracker checks they match the sealed report; it cannot know that the caller really re-read the store.
24. **Platform evidence:** Linux results are recorded under `results/` with their exact environment. Windows was **not executed** by the authors of this revision; `.github/workflows/tests.yml` runs the suite on `windows-latest`, and the Windows-sensitive code paths (temp-dir cleanup with SQLite, `os.replace`, UTF-8 subprocess output, temp-path masking) were adapted by reading, not by running. Treat Windows as unverified until its own run record exists.
25. **Package test runner:** the Linux runs recorded in this revision used a small stand-in test runner because `pytest` could not be installed offline. Real `pytest` results exist only where a run record says so.
